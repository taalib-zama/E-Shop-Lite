## FRD - User Story 14: Notification Dispatch

**ID:** US-14  
**Service:** `notification-service` (`NOTIFICATION-SERVICE`)  
**Primary flow:** `order.finalized.v1` event -> notification record -> dispatch adapter  
**Status:** Ready for implementation

### 1) User Story
As a user, I want checkout result notifications so I receive confirmation or failure updates.

### 2) Business Rules
- Notification is triggered when order reaches terminal state.
- Each event results in at most one notification side effect (idempotent consumer).
- Notification status values: `PENDING`, `SENT`, `FAILED`.
- Dispatch failures are retried with backoff.
- No sensitive data (payment token, secrets) in message body.

### 3) Functional Requirements
Consumer input: `order.finalized.v1` event.

Optional query endpoint (internal/admin):
`GET /notifications/{id}`

Dispatch success example:
```json

```

### 4) Data Model
- `notifications(id, order_id, user_id, channel, template_key, payload_json, status, attempts, created_at, sent_at)`
- `processed_events(event_id, consumer_name, processed_at)` for idempotency.

### 5) Security, Observability, NFR
- Consumer path protected by broker/service trust boundary.
- Metrics: `notification_dispatch_total{outcome}`, `notification_dispatch_duration_seconds`, `notification_retry_total`.
- Logs include `traceId`, `eventId`, `orderId`, `notificationId`, `status`.
- p95 dispatch latency target `< 400ms` for mock adapter.
