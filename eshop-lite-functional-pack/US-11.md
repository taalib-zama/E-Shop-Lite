## FRD - User Story 11: Payment Authorization

**ID:** US-11  
**Service:** `payment-service` (`PAYMENT-SERVICE`)  
**Gateway route:** `POST /payments/authorize` -> `lb://PAYMENT-SERVICE/payments/authorize`  
**Status:** Ready for implementation

### 1) User Story
As a system, I want to authorize payment for reserved orders so orders can be confirmed.

### 2) Business Rules
- Payment authorization is attempted only for orders eligible for checkout (inventory already reserved).
- Payment state transitions: `INITIATED` -> `AUTHORIZED` or `FAILED`.
- Successful authorization emits `payment.authorized.v1`.
- Failed authorization emits `payment.failed.v1`.
- Idempotency key must prevent duplicate authorization side effects.

### 3) Functional Requirements
`POST /payments/authorize` (protected/internal)

Request example:
```json
{
  "orderId": "2f5d5485-9180-4e1f-9a4f-74f43dc8c718",
  "userId": "a6c5a0de-2b0f-4a1d-9c5d-1f02e0a5e9e2",
  "amount": 16997.00,
  "currency": "INR",
  "paymentMethod": {
    "type": "CARD",
    "token": "tok_abc123"
  }
}
```

Success `200`:
```json
{
  "paymentId": "a1e2c3d4-1111-2222-3333-444455556666",
  "orderId": "2f5d5485-9180-4e1f-9a4f-74f43dc8c718",
  "status": "AUTHORIZED",
  "authorizedAt": "2026-03-26T14:05:00Z"
}
```

Problem Details example `402/409` equivalent failure mapping:
```json
{
  "type": "https://eshop-lite/errors/payment-declined",
  "title": "Payment authorization failed",
  "status": 409,
  "detail": "Payment provider declined authorization",
  "traceId": "a1b2c3",
  "errors": []
}
```

### 4) Data Model
- `payments(id, order_id, user_id, amount, currency, method_type, status, provider_ref, failure_code, created_at, updated_at)`
- `payment_outbox_events(...)` or shared outbox table in payment service.

### 5) Security, Observability, NFR
- Protected endpoint; validate JWT/service auth.
- Never persist raw PAN/CVV; only payment token/reference.
- Metrics: `payment_authorize_requests_total`, `payment_authorize_duration_seconds`, `payment_authorize_failures_total`.
- Tracing and headers: propagate `Authorization`, `X-Request-Id`, `traceparent`.
- p95 authorize latency target `< 500ms` with mock provider.

### 7) QA Matrix
- **US11-P1** valid authorization -> `AUTHORIZED`.
- **US11-P2** emits `payment.authorized.v1` event.
- **US11-N1** provider decline -> failed response + event.
- **US11-N2** duplicate idempotency key no duplicate side effects.
- **US11-S1** missing token -> `401`.
- **US11-O1** payment metrics/logs/traces visible.

### 8) RestAssured Example
```java
RestAssured.given()
  .header("Authorization", "Bearer <service-token>")
  .header("Idempotency-Key", "pay-order-2f5d")
  .contentType("application/json")
  .body("{\"orderId\":\"2f5d...\",\"userId\":\"a6c5...\",\"amount\":16997.00,\"currency\":\"INR\",\"paymentMethod\":{\"type\":\"CARD\",\"token\":\"tok_abc123\"}}")
  .post("/payments/authorize")
  .then().statusCode(200);
```

### 9) OpenAPI Snippet
```yaml
paths:
  /payments/authorize:
    post:
      summary: Authorize payment
      security:
        - bearerAuth: []
      parameters:
        - in: header
          name: Idempotency-Key
          required: true
          schema: { type: string }
      responses:
        '200': { description: Payment authorized }
        '401': { description: Unauthorized }
        '409': { description: Authorization failed }
```
