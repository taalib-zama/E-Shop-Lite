## FRD - User Story 15: Reliability and Resilience Hardening

**ID:** US-15  
**Services:** `order-service`, `payment-service`, `notification-service`  
**Focus:** resilience policies + retry safety + end-to-end observability  
**Status:** Ready for implementation

### 1) User Story
As a platform, I want resilient payment and notification workflows so transient failures do not break checkout.

### 2) Business Rules
- Downstream calls must use timeout + bounded retry + circuit breaker.
- Fallback paths must keep workflow in recoverable state.
- Outbox dispatch retries must not lose events.
- Consumers must remain idempotent under duplicate delivery.
- Trace and request correlation must be preserved across sync/async boundaries.

### 3) Functional Requirements
Key technical requirements:
- OpenFeign clients for payment/notification integrations.
- Resilience4j policies per client instance.
- Outbox retry worker with exponential backoff.
- Dead-letter handling for irrecoverable events.

Recoverable order response example under payment dependency failure:
```json
{
  "orderId": "2f5d5485-9180-4e1f-9a4f-74f43dc8c718",
  "status": "PENDING_PAYMENT",
  "recoveryHint": "Payment dependency temporarily unavailable"
}
```

### 4) Security, Observability, NFR
- Header propagation: `Authorization`, `X-Request-Id`, `traceparent`.
- Metrics:
  - `resilience4j_retry_calls_total`
  - `resilience4j_circuitbreaker_state`
  - `outbox_publish_failures_total`
  - `notification_retry_total`
- Logs capture breaker transitions and retry attempts with `traceId`.
- NFR: avoid thread starvation and cascading timeout amplification.

### 6) QA Matrix
- **US15-P1** nominal path succeeds with resilience no-op.

- **US15-N3** fallback keeps workflow recoverable.
