## FRD - User Story 19: Reconciliation and Drift Detection

**ID:** US-19  
**Scope:** Cross-service consistency checks (order/payment/inventory)  
**Primary flow:** Scheduled reconciliation job + report artifact  
**Status:** Ready for implementation

### 1) User Story
As a platform, I want reconciliation checks so cross-service state drift is detected and recoverable.

### 2) Business Rules
- Reconciliation scans compare canonical states across services.
- Mismatches are categorized and reported with actionable hints.
- Job reruns are idempotent and auditable.
- No business side effects should occur during report-only mode.

### 3) Functional Requirements
Reconciliation categories (minimum):
- Order `CONFIRMED` but payment not `AUTHORIZED`
- Payment `AUTHORIZED` but order not finalized
- Cancelled order with inventory still reserved
- Missing event processing markers (outbox/consumer drift)

Report response example (`GET /ops/reconciliation/runs/{id}`):
```json
{
  "runId": "0d8f0d4d-2666-4e6f-bcc3-3b8ddf0f2c11",
  "startedAt": "2026-03-26T18:00:00Z",
  "status": "COMPLETED",
  "summary": {
    "scanned": 1200,
    "mismatches": 12
  },
  "categories": [
    { "type": "ORDER_PAYMENT_MISMATCH", "count": 5 },
    { "type": "INVENTORY_RELEASE_MISSING", "count": 7 }
  ]
}
```

Problem Details `404` example:

{

### 4) Data/Security/Observability/NFR
- Tables: `reconciliation_runs`, `reconciliation_findings`.
- Metrics: `reconciliation_runs_total`, `reconciliation_mismatches_total`, `reconciliation_duration_seconds`.
- Logs include `runId`, category counts, `traceId`.
- NFR: bounded scan window to avoid runtime degradation.

### 5) Tech Lead Guidance
- Implement scheduled job with chunked scans.
- Keep report generation and remediation separate initially.
- Add optional admin endpoint to trigger rerun.
- Store findings for audit/history.

### 6) QA Matrix
