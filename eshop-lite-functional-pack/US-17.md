## FRD - User Story 17: Resilience Policy Unification

**ID:** US-17  
**Scope:** Service-to-service and async reliability policies  
**Services:** `order-service`, `payment-service`, `inventory-service`, `notification-service`  
**Status:** Ready for implementation

### 1) User Story
As a platform, I want consistent timeout/retry/circuit-breaker policies so failure behavior is predictable.

### 2) Business Rules
- Each downstream client must have explicit timeout values.
- Retry attempts are bounded and backoff is defined.
- Circuit breakers open on sustained failure rates.
- Fallbacks must preserve recoverable business state.
- Policy names and tags are standardized for metrics.

### 3) Functional Requirements
Minimum policy profile:
- Timeout: connect `500ms`, read `1000ms` (adjust by endpoint class)
- Retry: max 3 attempts, short backoff
- Circuit breaker: sliding window + failure threshold
- Fallback: return recoverable status (`PENDING_*`) instead of hard-failing critical write paths

Fallback response example:
```json
{
  "orderId": "2f5d5485-9180-4e1f-9a4f-74f43dc8c718",
  "status": "PENDING_PAYMENT",
  "recoveryHint": "Dependency unavailable, retry scheduled"
}
```

### 4) Data/Security/Observability/NFR
- Metrics: `resilience4j_retry_calls_total`, `resilience4j_circuitbreaker_state`.
- Logs include breaker transitions and retry attempts with `traceId`.
- Traces include fallback spans.
- NFR: prevent thread starvation and cascading timeout amplification.

### 5) Tech Lead Guidance
- Keep a shared resilience config profile in config repo.
- Reuse consistent client instance names across services.
- Implement common interceptor for header propagation.
- Add chaos/fault injection tests in integration suite.

### 6) QA Matrix
